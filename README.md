## 这是什么


《智解甲骨·中医密码》—— Three.js 粒子点云 + MediaPipe 手势追踪的单文件网页交互作品。

作品分成**两个并列板块**，用底部控制栏最左侧的「甲骨文 / 中药」页签直接切换（共用同一套场景与手势输入）：

| 板块 | 内容 |
| --- | --- |
| **甲骨文** | 7000 粒子字形层：字库、任意字、五色、待机巡字、比心彩蛋 |
| **中药** | 两味药材：三七（5.9 万点，菊花心断面/饮片/皂苷）、雪上一枝蒿（2.4 万点，纺锤块根/白色断面/乌头碱）；属性卡内切换 |

切换是瞬时的（两个粒子层都常驻内存，只做显隐），不重新加载、不打断摄像头。

甲骨文板块的摄像头手势：

| 手势 | 效果 |
| --- | --- |
| 拇指食指捏合 | **聚形**：散落的星云气聚成甲骨文 |
| 张开手掌 | **气散**：字化气回归星云 |
| 捏着左右/上下移动 | **转动视图**：位置跟随（像方向盘），手到哪转到哪；满角左右 ±66°、上下 ±60° |
| 半握移动 | 牵引星云 |
| 双手 | 各带一枚气引点 |
| 拇指与食指交叉，中·无名·小指合在手心 | **比心**：气聚成 ❤，松手后落成「我爱你 / 三生三世」（见下「比心彩蛋」） |

无摄像头时自动回退鼠标模式：按住 = 捏合聚形，松开 = 气散；鼠标是相对设备，仍为「拖动＝旋转」。
比心是例外 —— 它需要真实的四指分工（中·无名·小指攥进手心、拇指与食指交叉），鼠标模式无法表达，仅在摄像头手势下可用。

### 比心彩蛋

**拇指与食指交叉成 X，中指·无名指·小指收进手心**，**持续保持约 0.45 秒**触发。

比心是**两段式**：7000 颗粒子先聚成一颗 ❤；松手约 1 秒后散开重聚成两行短语
「我爱你 / 三生三世」，停留约 5 秒，再回到比心前的那个字。整段期间手动点字库、
或待机巡字换字，都会立刻接管显示。

> 两个阶段**都不弹顶部红色横幅**（`#err` 那条是给错误/异常专用的，`position:fixed` 满宽暗红条，
> 拿来做形态播报既重复又抢眼）。画面中央的大字标签已经说明了当前形态。

实现上爱心与短语都**复用 `sampleGlyph3D` 的完整流水线** —— canvas 画形 → 扫墨迹 alpha →
生成目标点云，只是把「写什么字」换成「画一颗心」或「排一段话」，采样、顶点色、物理、
聚散、阵风惯性全部原样继承（`HEART_SPEC` / `drawHeartShape()` / `HEART_PHRASE_SPEC` /
`drawPhraseLines()` / `isHeartGesture()`）。

短语用的是新增的 `mode:'phrase'`：原流水线一次只能画一个字（居中单点 `fillText`），
七字放不下。`drawPhraseLines()` 按 `\n` 分行、逐字以 `fs*(1+PHRASE_GAP)` 步进居中排布，
字号仍走原有的「贴边就缩小重画」自适应。另外短语的包围盒又扁又宽（实测约 3.4×1.68），
若与单字同样归一到 `glyphW` 会在屏幕上明显偏小，故 `HEART_PHRASE_SPEC` 带
`glyphScale: 1.35` 单独放大（单字默认为 1，行为不变）。

判定用的是五条几何判据（`heartMetrics()` 一次算出、`isHeartGesture()` 逐条否决）。
全部以**跨掌宽 |5→17|** 归一化或取方向余弦，因此与手在画面中的远近、旋转都无关：

| # | 判据 | 常量 | 默认 |
| --- | --- | --- | --- |
| ① | 食指伸出去（指根到指尖长度 ÷ 跨掌宽） | `INDEX_LEN_MIN` | ≥ 0.55 |
| ② | 食指是竖起的（食指方向 · 掌轴方向） | `INDEX_UP_MIN` | ≥ 0.35 |
| ③ | 拇食指尖**分开**（距离 ÷ 跨掌宽） | `TIP_APART_MIN` | ≥ 0.25 |
| ④ | 拇指**跨过食指所在直线**：拇指根(2)与拇指尖(4)落在该直线两侧，且两侧余量都够 | `CROSS_DEPTH_MIN` | 深度 > 0.04 |
| ⑤ | 中·无名·小指收进手心（同一长度比） | `FOLD_LEN_MAX` | ≤ 0.60 |

实测量级（离线回归）：手指**伸直 ≈ 1.0~1.3**，**收进手心 ≈ 0.15~0.20**。阈值落在中间，两侧余量都大。

### ④ 为什么要用「跨线」而不是「两段相交」

这是本轮最关键的一处改动。原先判的是「拇指段(2-4) 与食指段(5-8) 在画面上相交」，用叉积做
**严格的线段相交**检验。实采数据里，这个判据单帧只有 **19.5%** 的帧成立 —— 也就是说
**主判据基本上是死的**，能否触发一直靠"指尖换位"那条兜底在撑。

原因不在阈值松紧：交叉处两指互相遮挡，MediaPipe 的关键点在那里会来回跳，而"两段是否相交"
是个**脆弱的拓扑判断** —— 关键点一抖，交点就在"存在/不存在"之间翻转。

换成「跨线」后，判的是**拇指根与拇指尖相对食指直线的侧号是否相反**。符号翻转是整数变化，
只要拇指真的从一侧伸到了另一侧，符号就稳定为异号。同时 `overDepth`（两侧的最小余量）
能排除"擦着线过去"的模棱两可。

量化对比（合成手型 + σ=0.005 的抖动，≈3.2px @640，各 3000 次）：

| 手型 | 旧：段相交 | 新：跨线 | 新：完整判定 | 期望 |
| --- | --- | --- | --- | --- |
| **目标手势** | **3.1%** | **100%** | **100%** ✓ | 真 |
| V 手势（两指张开） | 0% | 0% | 0% ✓ | 假 |
| 普通捏合 | 28.9% | 7.8% | 0% ✓ | 假（被 ③ 挡住） |
| 手枪 | 0% | 100% | 0% ✓ | 假（被 ② 挡住） |
| 握拳 | 1.3% | 75.7% | 0.2% ✓ | 假（被 ① 挡住） |

目标手势 **3.1% → 100%**，而四类误判依然全部挡得住 —— 因为 ①②③ 各守一类。

### 两个必须踩过才知道的坑

**① 尺度参照会塌缩。** 最初用「指尖到掌心 ÷ 指根到掌心」度量伸展，掌心取腕(0)与中指根(9)的
中点。实采 3685 帧后发现：手一旦朝镜头方向倾，|0→9| 在 2D 上变得很短，分母趋零，比值被放大到
**5.94** 这种荒谬值（中指收起来不可能超过 2.5），于是「三指收起」的通过率恒为 **0%**，手势摆得
再标准也永不触发。现在只用 |5→17|（跨掌宽）作唯一尺度 —— 它只取决于手掌宽度，与手指蜷伸、
手掌朝向都无关。

**② 单帧信号本身带噪，必须做时间平滑。** 实采 3918 帧（同一姿势保持）的单帧通过率是：
食指长 99.5% / 上举 89% / 指尖距 86% / 三指收起 6.6% / **两段相交 19.5%** / 全达成 0.1%。
上表 100% 是**理想合成数据**下的结果，真机上仍有残留抖动。所以判定不直接用单帧值：
`heartEmaOf()` 先对度量做 EMA（`HEART_EMA_A = 0.22`，约 4~5 帧时间常数），
交叉则取"最近若干帧里成立的比例"（`crossRate > 0.5` 即认定在交叉）。

**③ 「一丢就清零」会让持续计时永远攒不满。** 原先任何一帧判失败就 `heartSince = 0`。
手保持同一姿势时，关键点仍会偶尔判丢一两帧，于是 450ms 窗口反复归零。
现在记「最后一次成立时刻」`heartOkAt`，只有连续丢失超过 `HEART_GRACE_MS = 220` 才真正清零，
短暂丢帧只是暂停计时。

> 端到端验证：把合成关键点直接灌进 `handleLms()`，输入序列是 `heart, heart, v` 循环
> （每 120ms 就夹一个判失败帧）。结果 `phase=1`、`hold=762ms`、`glyph="比心"` ——
> **断续输入也能触发**。旧逻辑下每次 `v` 都会清零，这种输入永远不可能触发。

**④ 平滑状态必须每只手各存一份。** 原先 `heartEma` 是全局单例，两只手同时入画时，
左手和右手会交替往同一组数上喂值，度量被搅成两手的平均 —— 两只都判不出来。
现在挂到手的对象上（`h._heartE`），互不干扰。

各判据挡掉的误判，**没有一条是冗余的**：

- **③ 指尖必须分开** —— 交叉的两指在交叉点两侧、指尖必然分开；而「捏合聚形」是拇食指**相触**。
  少了它，拇指尖贴到食指尖时可能判成"跨过轴线"，捏合会蹦出爱心。
- **② 食指必须竖起** —— 换成跨线判据后，这条从"辅助"变成了**必需**：「手枪手势」（拇指竖、
  食指横）里拇指同样跨过了食指直线（实测 100% 成立），全靠 ② 挡住（它的上举余弦只有 0.16，
  阈值 0.35）。
- **① 食指长度** —— 同理，握拳时拇指横压四指也会"跨线"（75.7%），靠 ① 挡住（食指只有 0.40）。

> 也就是说：**跨线判据本身只回答"拇指有没有穿过去"，它不区分那是比心还是握拳/手枪。**
> 区分靠的是 ①②③⑤ 这四条 —— 动任何一条之前先想清楚它在挡哪一类。

> 另一个几何事实：不能只靠"指尖换位"判交叉 —— 拇指比食指短，交叉时拇指尖往往停在食指中段，
> 压根越不过食指尖（实测目标手势的换位值仍是负的）。所以主判据取跨线，换位只作兜底。

**为什么从旧判据换过来**：旧形态（拇指食指尖相触 + 余三指张开）与「捏合聚形」在几何上同构 ——
都是拇指食指尖相触，唯一差别是余指张开度，只能靠调阈值折中，误触无法根治。新形态里
**三指必须攥进手心、拇指与食指必须交叉**，与捏合的差别是拓扑级的。

离线回归覆盖 7 种手型（五指张开 / 手枪 / 拇食竖起不交叉 / 普通捏合 / 握拳 / 目标手势 /
交叉但中指伸着），期望 1 真 6 假，实测 7/7。

**手型校准**：地址栏在页面 URL 后加 `?dbg=1`，左下角会实时显示**平滑后**的各判据数值
与一条**持续进度条**：

```
比心手型度量（平滑后）  ✔ 成立
持续 ██████···· 60%
① 食指长  1.04  需 ≥ 0.55
② 上举余弦  0.72  需 ≥ 0.35
③ 指尖间距  1.45  需 ≥ 0.25
④ 跨线 是 深度 0.29  需 > 0.04
   交叉比例 0.86  需 > 0.50
⑤ 中指 0.20 无名 0.19 小指 0.18  需 ≤ 0.60
```

进度条是最实用的一项：**"为什么没触发"最常见的答案是"姿态对了，但没坚持够久"**。
只看到"✔ 成立"分不清是姿态不对还是时间不够，进度条一眼就能分辨。

| 常量 | 默认 | 管什么 | 怎么调 |
| --- | --- | --- | --- |
| `HEART_HOLD_MS` | 450 | 「稳不稳」—— 姿态要持续多久才认定 | 误触就加大，觉得迟钝就减小 |
| `HEART_GRACE_MS` | 220 | 短暂判丢的宽容窗口 | 总差一点点触发就加大；误触就减小 |
| `CROSS_DEPTH_MIN` | 0.04 | 跨线要跨多深才算真交叉 | 误触就加大（0.10 只认明显的交叉） |
| `HEART_PHRASE_MS` | 5200 | 短语停留多久再还原成原字 | 想多欣赏一会儿就调大 |

**为什么用时间而不是「连续 N 帧」**：MediaPipe 检测帧率会随机型与负载大幅漂移
（本机实测达数十帧/秒，一次 6 秒窗口回传了 1455 次结果）。原先的「连续 3 帧」
实际只有几十毫秒，普通捏合时手指微张的瞬时抖动就能满足，
导致横幅「比心 ❤ · 气聚成爱」在没人刻意做手势时反复弹出。改成按毫秒累计后即稳定。

> 没有摄像头也想出爱心：底部「任意字·楷体」直接输入 `❤` 即可（走楷体分支，同样出粒子爱心）。
>
> 想换成别的句子：改 `HEART_PHRASE_SPEC` 的 `ch`（用 `\n` 分行，建议每行 3~4 字）与
> `labelCh`（标签用，避免 `\n` 在 HTML 里被折叠成空格）即可，字号自适应与粒子密度会自动跟随。

聚形收敛期间视图锁定为正视（成字那一瞬一定是正的），成字后才交还转动控制权。左下角为实时手部骨架（不显示相机画面）。

## 🌿 中药板块：三七 · 铜皮铁骨

点底部控制栏的「中药」页签进入。它不是一株植物标本，而是按**中药**来读的一味药：
**张开手掌** → 主根前半截化尘散开，露出菊花心断面，三片饮片浮出，植株上浮让位；
**捏合** → 铜皮收拢、重新合成完整植株。无摄像头时按住鼠标即等于张掌。

**点击画面或手进入画面后**，主植株右侧才会另起一个药用部位的粒子小样
（三七：铜皮主根 + 芦头茎痕 + 支根/须根 + 菊花心饮片；雪上一枝蒿：三枚纺锤块根 + 须根 + 白色断面），
并配「药用部位 / MEDICINAL PART」标注，小样中心另有一个脉动金色标点直接钉在入药部位上；
右侧同时列出「使用方法 / HOW TO USE」：
三七 = 内服（研末冲服 1–3 g）· 煎汤（3–9 g）· 外用（撒敷/调敷）；
雪上一枝蒿 = 外用（调敷/泡酒涂擦）· 内服（极少量、须炮制遵医嘱）· 禁忌（孕妇、心脏病患者）。
小样与主枝拉开更远（按窗口安全边距自适应，桌面约 x=2.55）、
可**按住拖拽旋转**查看，未拖动时缓慢自转；外圈定位环已去掉，只留标注本身。

> 右上角原有的「神农采药」粒子小图已按用户要求移除（连同 CSS / DOM / 绘制脚本），
> 右侧空间让给药坊炮制演示的工序列。

界面文字全部中英双语：板块页签、中央标题、结构标签、属性卡（性味/归经/功效/鉴别/警示）都带英文注释。

**药性**（左下角常驻卡片，不随视角旋转）：

| 项目 | 内容 |
| --- | --- |
| 基原 | 五加科人参属三七 *Panax notoginseng* 的干燥根及根茎 |
| 性味 | 温，甘、微苦 |
| 归经 | 肝、胃经 |
| 功效 | 化瘀止血，活血定痛 |
| 鉴别 | 铜皮铁骨 · 菊花心 |

植株形态按药材学细节做：

- **主根**：芦头（顶部二次收细）+ 三圈茎痕（判断生长年限）+ 纵向棱脊 + 两处瘤状突起 + 横向环纹。
- **三枝七叶**：掌状复叶，三枝各七小叶；叶缘有锯齿，主脉与六对侧脉单独提亮 —— 21 片叶全靠脉才数得清。
- **花与果**：伞形花序上绿白色五瓣小花与红色浆果混生（果期）。
- **饮片**：散气时主根左侧浮出三片小圆片，与断面同一套菊花心画法。
- **皂苷**：四个并环 + 两个糖环（Rg₁/Rb₁ 的示意），绕自身中心缓慢自转。

共 **9 个标签**：主根·铜皮、支根、须根、茎、叶·三枝七叶、红果·花、菊花心·断面、
皂苷 Rg₁/Rb₁、饮片·菊花心。标签只在 `open > 0.26` 时渐显 —— 闭合时一堆字糊在植株上只会挡住形体。

实现要点：

| 结构 | 做法 |
| --- | --- |
| 主根 | `sanqiRootSurface()`：Fibonacci 球面 + 芦头收细 + 3 瓣棱脊 + 高斯瘤突 + 横向环纹，避免"鹅卵石" |
| 断面 | 极坐标撒点：底色铺满，叠 24 条短射线与四道同心环；亮度 = `open^0.7` |
| 茎 / 叶柄 / 花葶 | `sanqiTube()`：Catmull-Rom 折线 + 环向正交基，拐弯处不会拧麻花 |
| 叶 | 椭圆面片 + 叶面微凹 + 锯齿缘 + 主脉/六对侧脉 |
| 花 | `sanqiFlower()`：五瓣 + 花心，与红果同伞序 |
| 饮片 | `sanqiSlice()`：缩小版菊花心，绕 Y/X 倾斜 |
| 皂苷 | 四个并环 + 两个糖环，散气时自转 |

共 **5.86 万点**（实测 `SANQI.n` = 58859）。散气时前半截主根按各自随机幅度外散、上飘，
后半截留作背景；断面与根须不动，植株只上浮 —— 这是「打开看药材」，不是「拆模型」。

> 与字形层的关系：三七单开一套粒子缓冲（`SANQI`），显隐互斥；进入后字形层隐藏、

### 背景：药坊炮制演示

整屏叠一层 2D 背景（`#workshop` + `#workshopCv`，`z-index:0`，在 3D 画布之后），画一套传统药坊的炮制工序，随药材切换：

| 三七（5 道） | 雪上一枝蒿（4 道） |
| --- | --- |
| 洗净 → 蒸制 → 切片 → 晾晒 → 研粉 | 洗净 → 酒炙 → 甘草制 → 晒干 |

- **每道工序都有一个动漫小人在操作**：Q 版药童（大头、圆脸、发髻、道袍、腰带、布鞋），画成扁平色块而非线框。他站在器具左侧、与器具共用一条地线，按工序换姿势与道具：洗净时双手在盆里搓洗（前倾）、蒸制时持扇扇火、切片时举刀一顿一顿下劈、晾晒时双手举起药材翻动、研粉时双手扶碾杆往复推、酒炙时拎酒壶倾倒、甘草制时持勺搅锅。当前这道做完整套动作；其余工序做**待机微动**（重心缓慢左右倒、上身轻摆），不是定格。
- **动画按业界动画原则逐条落实**（2026-11-18 一轮专门优化，全部用数值验证而非肉眼）：
  - **手型随工具分化**：`armIK` 增加 `handShape` 参数，五种手型 —— `grip` 握（刀柄/扇柄/勺柄/碾杆，手指蜷成一圈、拇指横压）、`flat` 按（按药材/扶板面，四指伸直）、`cup` 托（托腕/扶杆，指腹向上兜）、`pinch` 捏（捏饮片，食指与拇指对捏）、`open` 张（松手放药）。上一版七道工序共用一种"并拢微扣"的手，握刀和扇扇子看起来是同一只手换了道具。
  - **预备动作（anticipation）**：切片落刀前先多蓄 0.09 的额外抬升，然后才加速落下 —— 少了这段反向运动，刀看起来是被"放"下去的，不是被"砍"下去的。`fall()` 增加了 `antic` 参数，末端用 `sin` 包络归零，实测接缝仅 0.000019，仍 C0 连续。
  - **跟随动作（follow-through）**：扇面比手腕滞后 0.55rad、勺头滞后 0.5rad、刀刃抬刀时滞后 0.10rad 而落刀触板时略超前。手已经停住，工具还在回弹，这是"有质量"的直接证据。
  - **次要动作（secondary action）**：衣摆随前倾量甩出并带低频风动（行程 1.6px）、腰带两条穗子错相位摆动（2.8px）、发髻随转头反向滞后（`bunLagX`）。布料与木头最直观的区别就在这里。
  - **挤压拉伸（squash & stretch）**：呼吸时胸腔横向微胀 0.6%、肩线上抬，只作用于袍身（画完立即 `restore`，手臂不被拉歪）；研粉推碾时碾轮压过药粉，人整体下沉 1.2% 再回弹。
  - **眨眼**：从"`blink > 0.55` 二值切换"（单帧跳变 1.0，等于眼睛瞬间开合）改成按比例纵向压扁眼睑（单帧跳变降到 0.10），并加入偶发双眨；实测闭眼时间占 1.77%，接近真人。
  - **眼神微动**：瞳孔叠加两层极慢的 saccade 漂移（约 0.6% 头径、周期 2–4 秒），眼睛不再钉死。
  - **过渡连续性**：切换工序时手部动作用 `amt` 权重在 0.45s 内淡入（"工作位 ↔ 垂手位"直线插值），实测每帧位移 ≤3.4px、均匀度约 1.0，不再瞬移。
  - **曲线体检**：`pour()` 原有两处真实跳变（x=0.58 抖 0.022、x=0.70 跳 0.10 即满量程 10%，酒壶会"猛地弹起再落下"），改为分段拼接 + `sin²(kπ)` 包络后，最大单步跳变 0.000311、尖峰比从 242244 降到 1.1。
- **器物同样改为扁平上色**：木盆（木纹渐变 + 水面波纹 + 漂着的根 + 气泡）、三层蒸甑（灶膛火光 + 竹箍 + 三缕蒸汽）、砧板与药刀（刀身有金属渐变，起落切片）、晾药架（三层药材随风轻摆 + 斜下暖光）、碾槽碾轮（槽内药粉 + 飘起粉尘）、酒坛酒壶（红布封口 + 滴落酒液）、药锅（金属锅身 + 汤面翻动 + 浮着的甘草片）。
- **每道工序可点击**：盖一层透明热区（`.pao-step`），点开弹出说明卡讲「这一步有什么用」——例如「酒炙能显著降低乌头碱毒性，同时引药上行、增强止痛之力」「甘草与乌头类同煮可减毒」。热区只在**中药模式且未进部位视图**时可点（`body.herb-mode:not(.part-open)`），甲骨文模式下不会误弹；相邻热区竖向范围收在 1.84u（格距 2.10u），点第 3 道不会命中第 2 道。
- **节拍**：每道停留 4.6 秒（3.4 秒时动作还没做完就切走），换格时新旧两道用 0.5s 交叉淡入淡出，不再是硬切跳片。
- **布局**：炮制工艺全部排在**右侧一列**（`01 → 05` 自上而下），左侧留给药材卡与植株，中间留白。整条流水线读起来就是「怎么做」的顺序，不再拆成两组。改窗口尺寸会重排（每 18 帧比对一次，避免逐帧量 `getBoundingClientRect` 引发布局抖动）。字号与间距按「每格占 1.82u」推算（`unit = gap / 2.62`），实测相邻两格留出 50–53px 空隙，文字落在脚线以下、不压下一格的人。
- **不抢画面的做法**：底色保持纯黑（画布 `alpha:true` + `setClearColor(0,0)`，不再 `scene.background`），背景只在底部铺一层极淡暖雾当地气，光柱压到 1% 透明度 —— 早期版本铺了整屏径向渐变，结果把昏暗的黑底洗成灰橄榄色，粒子立刻发灰。
- **进入部位视图时背景降到 6%**（`body.part-open`）：那时画面要放部位、化学式、结构、切面，工序图讲的是"怎么做"，留着只会干扰。
- 窄屏（≤760px）隐藏背景。

## 快速开始

摄像头手势必须在 `http://` 或 `https://` 下运行（`file://` 会被浏览器拦截：Safari 在 `file://` 下允许摄像头，却禁止 `fetch` 本地 wasm，报错只有一句 "Load failed"）：

```bash
cd /path/to/甲骨文      # 必须在项目目录下执行：serve.py 是相对路径
python3 serve.py 8138
# 浏览器打开 http://localhost:8138/ —— 欢迎页点「进入展览」后进入作品
```

macOS 上还可以直接**双击**项目根目录的 [`启动本地服务.command`](启动本地服务.command)：
它会自动切到本目录、检测端口是否已占用、起服务并打开浏览器。同目录另有一份
`启动本地服务（仅本机）.command`，只监听 `127.0.0.1`，在不可信 Wi-Fi 下用这个。
关掉终端窗口服务就停了 —— 请用 Control-C 退出，别直接强杀，否则残留进程会占着 8138 端口，
下次双击会误报「端口被占用」。

**为什么 `http://localhost` 明文也能拿到摄像头**：按 W3C《Secure Contexts》规范 3.1 节，
host 为 `localhost`（以及 `127.0.0.0/8`、`::1/128`）的源被视为「潜在可信」，
故明文 HTTP 下同样是安全上下文，`navigator.mediaDevices` 存在。
换成局域网 IP（如 `http://192.168.1.5:8138`）就**不是**安全上下文，手势会失效 ——
这是浏览器规则，与本项目无关。

`serve.py` 是无缓存、多线程的静态服务器（只依赖标准库）。页面对此有前置拦截：在 `file://` 下点击「手势控制」会直接提示改用 HTTP，而不是抛出一句看不懂的报错。

用 `python3 -m http.server 8138` 也能跑，但浏览器容易吃缓存，且它是单线程、一个挂起连接就会让整站停止响应，不推荐。

### 摄像头排查：被嵌在 iframe / 预览面板里一定不行（2026-10-23 逐场景实测）

同一份作品、同一台机器、同一枚 `Integrated Camera`，只因打开方式不同而结果不同：

| 打开方式 | 结果 |
| --- | --- |
| 独立浏览器窗口（`http://127.0.0.1:8138`） | ✅ 640×480 取流成功、推理稳定运行 |
| `index.html` 用 `document.write` 换入的作品页 | ✅ 成功 |
| **同源** iframe | ✅ 成功（Permissions Policy 默认 allowlist 是 `self`） |
| **跨域** iframe / App 内置预览面板 | ❌ `NotAllowedError: Permission denied` |

最后一行是**环境限制而非作品故障**：`getUserMedia` 在跨域 iframe 中会被 Permissions
Policy 直接拦下，连五种约束（含裸 `{video:true}`）都试不出来。**它的错误码与
「用户在弹窗点了拒绝」完全相同**，只靠 `error.name` 分不出来 —— 所以本项目额外
判断 `self !== top && 读不到 top.location`（`crossOriginFramed()`），并在**点击前**
就把按钮置灰附上引导，点击后也给出指向明确的原因而不是一句 "Permission denied"。

自查清单（按命中概率排序）：

1. 是不是在 IDE / App 的内置预览面板里打开的 → **换系统浏览器**，地址栏手输 `http://127.0.0.1:8138/index.html`
2. 是不是用了局域网 IP（`http://192.168.x.x:8138`）→ 不是安全上下文，改用 `localhost` / `127.0.0.1`
3. 摄像头是不是被别的应用占着（`NotReadableError`）→ 关掉微信 / 钉钉 / 腾讯会议 / 拍照机
4. 是不是上次点了「拒绝」（`NotAllowedError` 且非嵌套）→ 点地址栏摄像头图标改回「允许」再刷新
5. Windows「设置 → 隐私 → 相机」是否被关（设备本身正常、但隐私总闸是 Allow 还是 Off，是两回事）

> 数据表另有 155 条**多字条目**（`又/右/有/侑/佑/祐`、`月/夕` 这类同码位异体，以及 `祖乙`、`妣庚` 这类合文），**不进面板列表**：一个码位只对应一个字形，整条列出会显示成一长串、渲染时还会在同一画布上画多处文字互相遮挡。这些条目里每个字都收进了别名表，因此**输入单字照常能查到甲骨文**（如输入「右」→ U60491、「月」→ U605E0）。
>
> 面板按「人工编排的 67 字优先、其余按字表顺序」排列 —— 因为待机会自动巡下一字（每字约 18.4 秒），若让 1100 多个通用字混在前面，开场先看到的会是「一」「丁」「乙」这类与中医无关的字，精心挑的那批反被淹没。

## 操作速查

- 字库：控制条「字形 ▾」→ **左侧列表栏**（每行 = 字形 + 标题 + 简介，像阅读列表；可滚动，临近底部自动续载）+ 搜索（字 / 拼音 / 释义）
- 点列表条目 → 显示该字形；**再点同一条 → 隐藏**（标题与释义一并清空）。面板不自动收起，便于连续切换
- 底部「任意字·楷体」输入：**先查字库** —— 若该字有甲骨文字形，就用甲骨文渲染；库里没有才退回系统楷体（是楷体粒子字，不是甲骨文）。简繁都能查到（输入简体 `册`/`麦` 也会命中 `冊`/`麥` 的甲骨文字形），多字合并条目里的字（如 `月/夕` 的「月」）同样可查
- 颜色：五色预设（金青朱玉紫）+ 取色棒（屏幕吸管 / 系统取色盘 / 内置色板三级降级，长按取色棒唤出色板）；实时写入顶点色
- 板块切换：底部控制栏「甲骨文 / 中药」（窄屏显示为「甲 / 药」）；中药板块只保留「手势控制 / 全屏」，字形与配色入口自动收起
- 中药板块：捏合合株、张开手掌看铜皮化尘、菊花心断面、三片饮片与皂苷
- 药材切换：中药板块底部控制栏「药材 ▾」，弹出三七 / 雪上一枝蒿
- 药用部位：点击画面或挥手后，右侧出现粒子小样；部位上有金色标点，旁列「使用方法」，可拖拽旋转
- 背景：左右两侧滚动演示药坊炮制工序（洗净 / 蒸制 / 切片 / 晾晒 / 研粉；雪上一枝蒿为洗净 / 酒炙 / 甘草制 / 晒干），进入部位视图时自动压暗
- 全屏：控制条「⛶ 全屏」
- 待机巡字：进页面后连续 45 秒无输入才启动，此后每字约 18.4 秒（聚形 1.6s → 保持 12s → 散开 1.8s → 空歇 3s），一轮 67 字约 20.5 分钟；**只在精选的 67 字里轮播**（数据里标了 `curated: true` 的字），不会轮到全库中与中医无关的字；手动选字后计时重置，若所选字不在精选池里，巡字会安全接回池首（「心」）

## 目录结构

| 路径 | 说明 |
| --- | --- |
| `index.html` | 站点入口：**云南中医药大学欢迎页** + 后台预载 `gesture3d.html`（显示进度，点「进入展览」换入；静态托管的目录入口必须是 index.html，否则根地址 404） |
| `gesture3d.html` | 作品主页面。字体子集与字库全部内嵌，自包含 |
| `libs/` | Three.js r152 与 MediaPipe Hands 本地运行时（约 28MB，首次访问付一次，之后走长缓存） |
| `data/` | 字表数据库（1530 行已释甲骨文）与人工编排条目 |
| `add_glyphs.py` | 往精选字库加字：并入 `data/curated_glyphs.json` 后自动调用 `build_glyphs.py` |
| `build_glyphs.py` | 唯一的构建实现：重子集化字体 + 注入页面 + 刷新别名表与计数 |
| `data/curated_glyphs.json` | **人工编排层的唯一数据源**（字头、码位、精选标记、文案） |
| `serve.py` | 无缓存本地服务器（可选）：`python3 serve.py [端口]`，默认 8138，仅本机用 `--host 127.0.0.1` |
| `deploy.py` | 生成上传就绪的站点目录 `dist/`（只挑运行时必需文件，见「部署」） |
| `deploy/` | 自建服务器辅助：`setup-server.sh` 一键配 nginx，`README.md` 说明顺序与易错点 |

## 扩充字库

```bash
python3 add_glyphs.py 牛 虎 鹿
```

新字会被并入 `data/curated_glyphs.json`（带上 `curated` 标记，因而进入待机巡字池），随后自动调用 `build_glyphs.py` 完成字体子集化与页面注入。需要 `pip install fonttools`，字必须在数据表中。刷新页面即可生效。

数据分两层，职责不重叠：

| 层 | 文件 | 作用 |
| --- | --- | --- |
| 权威字表 | `data/oracle_glyphs_full.json` | 全部已释甲骨文（字头 ↔ 码位 ↔ 拼音 ↔ 释义） |
| 人工编排 | `data/curated_glyphs.json` | 人工润色过的条目 + 精选标记，**加字只改这里** |

`build_glyphs.py` 是唯一的构建实现（`add_glyphs.py` 也复用它）：

```bash
python3 build_glyphs.py              # 全量重建（读上表两个数据文件）
python3 build_glyphs.py --limit 200  # 只取前 200 个，试体积用
python3 build_glyphs.py --db 其它.json --curated 其它.json   # 换数据源
```

实测体积：面板约 1066 个单字，字体子集（二进制）约 **962KB**、页面内嵌 base64 约 **1.25MB**、整个 HTML 约 **1.5MB**（相比手势模型的 16MB 仍属小头）。字库数据已与主脚本分离：条目与别名表写在页面头部，重建只改动那两块。

## 部署

**硬性前提：必须 HTTPS。** 非 `localhost` 的 HTTP 页面不是「安全上下文」，浏览器**不提供摄像头**，手势功能直接不可用。GitHub Pages 自带 HTTPS；自建服务器需自行配证书。

### 方式一：GitHub Pages

**线上地址：<https://haikethreat.github.io/Oracle-bone-TCM/>**（2026-10-16 实测已上线）

配置：仓库 **Settings → Pages → Deploy from a branch** 选 `main` / `(root)`。
资源全部使用相对路径，已实测子路径（`用户名.github.io/仓库名/`）下可正常运行。
`Enforce HTTPS` 是默认域名下的**强制项**，会自动勾选 —— 正好满足摄像头对安全上下文的要求。

#### 首屏与手势是两条独立的下载路径（重要）

页面用 JS 注入只急加载 `three.min.js`（633KB）+ `hands.js`（45KB），**手势模型是点击才加载**的：

| 功能 | 需要下载 | 大陆实测 |
| --- | --- | --- |
| 打开页面 / 待机自动巡字 / 输入框生成 | 约 **680KB** | ✅ 1~3 秒 |
| 点「🎥 手势控制」 | 再加约 **16MB** 模型 | ✅ 数秒（自动择优源，见下） |

#### 已知坑与修复：Pages 上 6MB 的 `.wasm` 吞吐极不稳定（2026-10-16 实测 → 当晚修复）

同一宿主的对照测试结果非常反直觉：

| 文件 | 大小 | 实测速度 |
| --- | --- | --- |
| `three.min.js` | 633KB | **314 KB/s**（2 秒完成） |
| `hand_landmark_full.tflite` | 5.4MB | **703 KB/s** ✅ |
| `hands_solution_simd_wasm_bin.wasm` | 6.0MB | **11 ~ 83 KB/s** ❌ |

同一个文件在不同时刻测出 11 / 41 / 62 / 66 / 83 KB/s —— 而**同一宿主的 tflite 却有 703 KB/s**。
所以这**不是**「GitHub Pages 被墙」，也不是配置问题，而是这条 6MB 二进制路径被限速
（`.wasm` 已被 gzip，压缩比有限，疑似触发 CDN 流式压缩瓶颈）。

**已修复（2026-10-16 晚）：手势模型资源「就近择优」加载。**
启动手势前对三个源各发一个 550B 小文件探测请求（赛跑式，谁先连通用谁）：
① 本地 `libs/`（离线/局域网部署秒赢，行为与从前完全一致）；
② 淘宝 npmmirror（`registry.npmmirror.com`，阿里 CDN，**大陆实测 5.6 MB/s**）；
③ jsDelivr（`cdn.jsdelivr.net`，海外兜底，实测 1.5 MB/s）。
三个源与本地文件**逐字节同源**：同为 npm 包 `@mediapipe/hands@0.4.1675469240`（md5 已核对），
只换「送货地址」，模型本身零变化。整套约 16MB 模型在大陆数秒内下完；
三源全失败时回落本地，交给原有错误路径提示。源码：`gesture3d.html` 的 `HANDS_SOURCES / pickHandsSource()`。

#### 其他 Pages 事实（便于日后排查）

- `.wasm` 的 `Content-Type` 为 **`application/wasm`** ✅（不会让 MediaPipe 走慢速回退）
- **含 `.wasm` 在内全部走 gzip**：`gesture3d.html` 1,624,785B → **869,479B**（省 46.5%）
- `Cache-Control: max-age=600` —— Pages 固定值，**后台改不了**；页面靠顶部 `ASSET_V` 破缓存
- HTTP 强制 301 跳 HTTPS；108/110/111 三个边缘 IP 内容一致

### 方式二：自建服务器（阿里云等）

先生成上传就绪的目录，再上传并配置服务器：

```bash
python3 deploy.py                                  # ① 本地：输出 dist/，16 个文件约 25MB
rsync -avz --delete dist/ root@<ECS公网IP>:/var/www/oracletcm/   # ② 上传
sudo bash deploy/setup-server.sh oracletcm.com /var/www/oracletcm  # ③ 服务器：配 nginx
```

`deploy/setup-server.sh` 会装 nginx、写入下文那份配置、放行防火墙；它是幂等的，
且**先探测证书** —— 没有证书时先写「仅 HTTP」配置让站点能开（否则 nginx 因引用不存在的
证书而起不来），证书就绪后重跑即自动切换为 HTTPS。详见 [`deploy/README.md`](deploy/README.md)。

脚本只挑**运行时真正需要**的文件，并显式保留两类「没被请求但删不得」的 fallback：
`hands_solution_wasm_bin.{js,wasm}`（旧浏览器无 SIMD 时用）与 `hand_landmark_lite.tflite`（`modelComplexity:0` 时用）。
不纳入 `libs/AYJGW.ttf`（4.2MB）—— 那是构建时子集化用的完整字体，页面内嵌的是 base64 子集。

把 `dist/` 内容上传到站点根后，nginx 关键配置：

```nginx
server {
    listen 443 ssl http2;
    server_name 你的域名;
    ssl_certificate     /etc/nginx/ssl/你的域名.pem;
    ssl_certificate_key /etc/nginx/ssl/你的域名.key;

    root /var/www/oracle;
    index index.html;

    # 必须：.wasm 的 MIME（默认 octet-stream 会让 MediaPipe 走慢速回退）
    types { application/wasm wasm; }
    include /etc/nginx/mime.types;

    gzip on;
    gzip_comp_level 6;
    gzip_min_length 1024;
    gzip_types text/html text/css application/javascript text/javascript application/json;

    # libs/ 长缓存（首屏约 16MB，只在首次付）；页面用顶部 ASSET_V 破缓存
    location /libs/ {
        add_header Cache-Control "public, max-age=31536000, immutable";
        gzip off;              # wasm/tflite 已是压缩格式，再压无益
        try_files $uri =404;
    }
    location ~ \.html$ { add_header Cache-Control "no-cache"; }

    client_max_body_size 32m;
}
server { listen 80; server_name 你的域名; return 301 https://$host$request_uri; }
```

压缩收益（实测）：`gesture3d.html` 1550→**831KB**、
`hands_solution_simd_wasm_bin.wasm` 5885→**1773KB**、`three.min.js` 618→**154KB**。

安全组只放行 **443**（与 80 用于跳转）。**不要把 `serve.py` 的 8138 端口暴露到公网** —— 它面向本地开发，没有访问控制。
